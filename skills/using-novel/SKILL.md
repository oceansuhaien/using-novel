# 小说技能入口

## 作用

本技能是 `novel-driver` 插件的总入口，只负责判断任务该交给哪个小说技能，不替代具体技能做完整创作，也**不在此处维护技能清单**。

- 每个小说技能的触发条件由其自身 `SKILL.md` 的 frontmatter `description` 声明，作为去中心化路由的权威源。
- 插件根 `README.md` 的命令表与技能表由 `scripts/generate-readme.ps1` 从 frontmatter 自动生成，`scripts/quick-validate.ps1` 会在漂移时报错。
- 本入口只保留跨技能方法论、组合编排、兜底与自检——这些是任何单个子技能 frontmatter 无法表达的跨域知识。

共享目录、证据等级、同步策略只放在 `novel-system-reference`，不在本入口重复维护。多轮确认后的 `context.md` 协议也属共享规则层；本入口只负责提醒子技能遵守。

## 路由方法论

1. 用户明确点名的技能优先。
2. 用户使用 `/using-novel` 时，依据各子技能 `description` 自动判断意图并分流。
3. 用户请求跨多个领域时，按下方"组合规则"排队执行，不要并行。
4. 缺少信息但不影响路由时，不要先盘问，直接进入最合适的技能。

## 注意！！！这很重要，如果找不到技能，可在当前项目根目录下的skills文件夹下面加载技能，加载失败不要进行下一步！！！，/using-novel 需要调用skill才可以工作！！！

## 开工前预检（强制）

在把任务交给任何一个小说子技能（`novel-outline-coach`、`novel-plot-weaver`、`novel-character-card-coach`、`novel-scene-writer`、`novel-system-reference`）之前，必须先判断当前工作目录属于哪一种环境。未完成预检前禁止进入子技能，也禁止向任何目录写回小说资料。

`novel-book-scaffold` 是例外：它本身就是用来新建/补齐工作区的，可以在预检得出"需要建书"结论后直接调用，不要求 cwd 已经是合法书籍根。

### 判据

按下面顺序判断 cwd，命中一个就停下来，不再往下判：

1. **书籍根（强判据，四项全满足）**：`summary.md` 存在，`outline/`、`plot/`、`characters/` 三个目录都存在。
2. **插件仓库根**：`AGENTS.md` 存在，`skills/using-novel/SKILL.md` 存在。
3. **其他**：以上都不满足。

### 三种处理动作

**命中书籍根 → 正式模式**

- 把当前 cwd 当作本次会话的书籍根；所有回写路径以 cwd 为基准，绝不跳出当前目录。
- 向用户声明："检测到书籍根 `<cwd 名称>`，进入正式模式。"
- 然后正常路由到目标子技能。

**命中插件仓库根 → 测试模式**

- 不允许就地写回故事资料到仓库根或 `skills/`、`commands/` 等插件目录。
- 选择本次会话的目标书籍目录：
  - 用户在请求里已指定 book-id（例如"在 demo-book 下"）→ 使用该 id。
  - 未指定 id 时，先读取 `test/current-book.yaml`：显式指定的 book-id 仍然优先于配置文件；若配置文件存在且 `book_id` 指向的 `test/books/<book-id>/` 满足"书籍根强判据"，则使用该 id。
  - `test/current-book.yaml` 不存在时，检查 `test/books/demo-book/` 是否满足"书籍根强判据"；满足则默认用 `demo-book`。
  - 配置文件存在但无效（例如缺少 `book_id`、目标目录不存在，或目标目录不满足书籍根强判据）时，必须停下来提示配置无效，并要求用户修正配置或显式指定 book-id；不能静默回退到 `demo-book`，也不能自行猜测其他书。
  - 配置文件不存在且 `demo-book` 也不满足强判据 → 停下来问一次："当前处于插件仓库根（测试模式），请选择：（a）在 `test/books/` 下新建一本书，请提供 book-id；（b）指定 `test/books/` 下已有的某本书 id；（c）取消。"
- 确认目标后，把该目录视为本次会话的书籍根，后续回写全部落在其内。
- 向用户声明："检测到插件仓库根，进入测试模式，目标书籍根 `test/books/<book-id>/`。"
- 目标目录不存在或未建齐时，先路由到 `novel-book-scaffold` 建齐，再进入原本请求的子技能。
- `test/current-book.yaml` 只服务于 `using-novel` 的测试模式选书，不是其他技能、脚本或正式模式共享的仓库级配置入口。

**其他目录 → 需用户确认**

- 不得自行假设"就地新建"或"去父级找书"，必须停下来问一次："当前目录既不是书籍根，也不是插件仓库根，请选择：（a）就地在当前目录初始化一本新书（会交给建书技能）；（b）切换到某个已有书籍根后重发；（c）取消本次操作。"
- 选 a 路由到 `novel-book-scaffold`，选 b 结束本轮等待用户切目录。

### 预检产物

进入子技能前，心里必须已经确定并在第一句回答里简述：

1. 当前模式（正式 / 测试 / 待确认）。
2. 本次会话的书籍根绝对路径。
3. 本次将路由的技能顺序。

## 组合规则

多个技能同时适用时按下列顺序串行执行，不要并行；原因是它们通常读写同一套单本书工作区资料。

- **先搭工作区再创作**（用户要"从零开始一本书"、创建本地工作区、测试书、示例书或补齐缺失目录时）：`novel-book-scaffold` → `novel-outline-coach` → 视后续目标继续进入 `novel-plot-weaver` 或 `novel-character-card-coach`。先把单本书目录契约落稳，后续技能才能回写到正确位置。
- **从想法到故事系统**（请求仍在高层构思阶段）：`novel-outline-coach` → `novel-plot-weaver` → `novel-character-card-coach`。先稳定题材、卖点和基础 canon，再细化剧情压力，最后把人物卡定型。
- **大纲 + 剧情**：`novel-outline-coach` → `novel-plot-weaver`。
- **剧情 + 人物**：默认 `novel-plot-weaver` → `novel-character-card-coach`；若真正卡住的是人物身份、动机或关系定位，先用 `novel-character-card-coach`。
- **大纲 + 人物**：`novel-outline-coach` → `novel-character-card-coach`。
- **剧情落成正文**：默认 `novel-plot-weaver` → `novel-scene-writer`。先把推进逻辑、节点和张力方向定住，再写正文；若当前缺口主要是人物身份、关系定位或首次出场识别信息不足，则改为 `novel-character-card-coach` → `novel-scene-writer`；若正文请求同时存在明显 continuity 断裂与人物识别断裂，可按 `novel-plot-weaver` → `novel-character-card-coach` → `novel-scene-writer` 串行补齐。
- **正文 + 人物口吻校正**：默认先用 `novel-scene-writer`；若问题根因其实是人物身份、动机或关系不稳，再串到 `novel-character-card-coach`。
- **剧情改写后的强制目录检查**：凡是通过 `using-novel` 发起写剧情、续写、扩写、润色、改写、修过渡，或任何会推动现有剧情的任务，不管当前落在 `novel-plot-weaver` 还是 `novel-scene-writer`，产出当前结果后都必须强制检查书籍目录里相关文件是否需要同步修改、补写或新增，不能跳过。默认至少检查：`plot/` 里的剧情节点、推进记录、伏笔与回收是否要改，`characters/` 里的人物卡、关系卡、人物索引是否要跟着改，`summary.md` 与 `context.md` 是否要记录新的稳定结论、冲突或待确认问题；确有必要时再继续检查 `outline/`、`canon/`、`inbox/` 与 `chapters/notes/`。像“剧情推进后要回看人物卡是否需要补设定或加新关系”“埋了新伏笔后要判断 `plot/foreshadowing` 或相关剧情文件是否需要补条目”都属于这一步的强制范围。
- **正文类请求的自动人物检查**：凡是通过 `using-novel` 发起写剧情、续写、扩写、润色、改写或修过渡，`novel-scene-writer` 给出当前结果后，`using-novel` 都要自动执行一次人物一致性检查。默认至少检查：人物口吻是否符合人物卡/身份/关系/当前情境，行为、动作、神态、反应是否符合性格、立场与环境压力，以及本段是否出现明显的人物设定失真或承接失真。除此之外，还要在两类场景里加做重点检查：首章、首场、新角色首次进场时，检查识别锚点是否足够、首次出场是否突兀；角色发生明显转换时，检查服侍关系、身份地位、情绪立场、性格表现等是否铺垫到位、结果不突兀。轻微问题先列出 1 到 3 个问题点，再给修正版；若根因是人物身份、动机、关系、绑定规则缺口，则自动串行转 `novel-character-card-coach`；若根因是剧情承接、节点目标或 continuity 缺口，则自动串行转 `novel-plot-weaver`；补齐后再回到正文链路。穿着、外貌呈现、能力边界可按需检查，但不是每轮默认硬性必检，也不把所有轻微状态波动都升级成问题，更不要为了修正文擅自发明新设定。
- **单域确认后的联动同步**：某技能已确认的改动清晰影响其他小说架构文件时，让当前技能按自己的同步规则一并更新；不要因为影响到另一个目录就机械切换技能。

## 执行要求

1. 用一句话说明将使用哪个技能或技能顺序，以及原因。
2. 调用选定技能并遵守该技能；若目标书籍根已有 `context.md`，默认把它视为共享上下文入口。
3. 目标书籍根缺少 `context.md` 且当前情境允许补齐工作区时，优先通过脚手架或增量补齐逻辑补上。
4. 组合流程还有下一步时，等当前技能完成后再进入下一技能。
5. 当当前技能完成后，如果本轮新增结论会明显影响其他小说架构模块，必须立刻做一次**串行补全扫描**，判断是否还需要继续进入下一个相关技能或更新相关目录，而不是停在单一技能结果。
6. 串行补全扫描至少检查这些目标：`context.md`、`summary.md`、`outline/`、`plot/`、`characters/`、`canon/`、`inbox/`，以及在确有必要时检查 `chapters/` 是否需要留下章节级观察或提纲占位。
7. 判断原则是“够继续写下去的最小闭环”：
   - 剧情讨论后，至少检查是否需要同步高层前提、人物定位、伏笔/卷钩子、未决问题与相关摘要。
   - 凡是写剧情、续写、扩写、润色、改写、修过渡，或任何导致剧情推进的结果，必须把“相关书籍目录文件是否需要修改、补写或新增”当作硬性收尾动作；不能只给当前文本结果就停下，至少要判断人物卡、关系卡、剧情节点、伏笔记录、相关摘要与上下文日志是否需要同步。
   - 大纲讨论后，至少检查是否需要同步卷纲、世界观压缩版、人物总览与待拍板问题。
   - 人物讨论后，至少检查是否需要同步关系卡、人物索引、主线连接方式与受影响的剧情摘要。
  - 正文场景讨论后，至少检查是否需要同步剧情节点、人物口吻约束、行为/反应是否贴人物设定与当前环境压力、上下场过渡、角色首次识别线索与相关摘要；若本轮是写剧情、续写、扩写、润色、改写或修过渡，还要自动执行一次人物一致性检查：轻微问题先列出 1 到 3 个问题点，再给修正版；结构性问题按根因自动串行转到 `novel-character-card-coach` 或 `novel-plot-weaver` 补齐后再回到正文链路。若本轮属于首章、首场、新角色首次进场，需重点检查识别锚点是否足够、首次出场是否突兀；若本轮出现角色明显转换，需重点检查服侍关系、身份地位、情绪立场、性格表现等是否铺垫到位，但不把所有轻微状态波动都升级成默认报警。
8. 若扫描后发现仍存在明显缺口，但缺口不会改变当前路由方向，则不要先提问，直接进入下一合适技能继续串行补齐；只有当缺口会改变路由或产生分叉时才提问。
9. 不要把完整技能列表先讲给用户——先路由，再工作。

## 正文请求的路由细化

当目标是写正文、续写、扩写、润色或修过渡时，先判断缺口属于哪一类：

- **可由 `novel-scene-writer` 直接兜底的轻缺口**：
  - 只缺相邻章节承接信息，但可通过 `context.md`、`summary.md`、相邻章节笔记/摘要与当前直接相关资料补齐。
  - 只缺角色在当前段落里的最小识别信息，且能用一句内的两个锚点稳住。
  - 这类情况可以直接进入 `novel-scene-writer`，由它按自己的输入规则处理。

- **应先转 `novel-plot-weaver` 的剧情缺口**：
  - 当前场景和前后章节为什么接在一起不清楚。
  - 这段要推进什么节点、承接什么冲突、处于什么节奏位置不清楚。
  - 只靠相邻章节资料仍然接不上，scene-writer 会被迫硬编过渡。

- **应先转 `novel-character-card-coach` 的人物缺口**：
  - 角色身份、关系、动机、立场不稳。
  - 角色第一次让读者需要认识时，连最小识别锚点都无从提取。
  - scene-writer 若继续写，会把人物写成“作者知道但读者不认识”的黑箱。

- **两类都重时**：
  - 先补剧情，再补人物，最后回到正文，即 `novel-plot-weaver` → `novel-character-card-coach` → `novel-scene-writer`。

判断原则仍然是“够继续写下去的最小闭环”：能由正文技能自己稳住的，不要升级成大串行；稳不住时再前置补齐。

## 串行补全扫描

这是 `using-novel` 作为入口技能的收尾职责，不是可选项。

### 何时触发

- 用户请求本身跨了多个小说域。
- 本轮讨论虽然起点只落在单一小说域，但输出结果已经明显影响其他域文件。
- 本轮属于写剧情、续写、扩写、润色、改写、修过渡，或任何会推动现有剧情的任务；这类请求默认必须触发，不能省略。
- 用户明确要求“顺手落盘”“别丢上下文”“完善设定”“补人物卡/大纲/worldbuilding/canon”等。

### 最低检查顺序

1. `context.md`：本轮是否形成了新的稳定确认、冲突、覆盖历史或待确认问题。
2. `summary.md`：是否需要同步新的高层稳定结论。
3. 当前主域目录：如 `plot/`、`outline/` 或 `characters/`。
4. 相邻受影响目录：
   - 剧情域常见相邻目录：`outline/`、`characters/`、`inbox/`
   - 大纲域常见相邻目录：`canon/`、`plot/`、`characters/`
   - 人物域常见相邻目录：`plot/`、`outline/`、`characters/relationships/`
   - 正文域常见相邻目录：`plot/`、`characters/`、`chapters/notes/`
5. 若本轮涉及剧情推进、改写、扩写、润色或新增伏笔，再强制追问一轮：人物卡要不要补，关系卡要不要补，`plot/foreshadowing` 或其他剧情文件要不要补，是否出现新的待确认问题要写进 `context.md`。
6. `canon/` 与 `chapters/`：只有在当前结论已经稳定到足以沉淀为背景设定或章节级观察时才进入。

### 退出条件

以下条件同时满足时，才可结束本轮 `using-novel` 串行流程：

- 当前主域结果已写稳。
- `context.md` 与 `summary.md` 已同步到位。
- 明显受影响的相邻目录已检查并补齐到“够继续写下去”的最小闭环。
- 如果本轮涉及剧情推进、改写、扩写、润色或新增伏笔，已明确判断人物卡、关系卡、剧情节点、伏笔记录等相关文件是“已同步”还是“暂不需要改”，而不是漏检。
- 剩余内容属于真正未拍板问题，而不是漏做的补全。

## 何时提问

只有在缺失信息会改变路由或阻止当前技能做出可靠结果时才提问。

合适的问题：

- "你现在是想先把这本书的工作区搭起来，还是直接在现有书籍目录里做大纲？"
- "这次更想先解决人物卡，还是剧情反转推进？"
- "高层设定已经定了吗？如果未定，我会先走大纲技能。"

不合适的做法：一开始收集所有偏好；把明确的剧情请求扩展成大访谈；因为可能还有上下文就拒绝路由。

## 兜底

请求不是建书脚手架、大纲、剧情、人物或资料规则时：

- 没有小说技能适用 → 直接正常回答。

## 自检

发现以下倾向时立刻纠正——正确做法是**有意识地路由**，而不是跳过技能或自行兼任：

- "这同时涉及剧情和人物，所以我自己全做。"
- "只要提到世界观，就一定是大纲技能。"
- "用户要先建书，所以后面的大纲需求先不管。"
- "用户要正文，所以小说插件没用。"
- "并行跑大纲和人物会更快。"
- "在这里再列一遍可路由技能清单会更方便。"（× 清单由 frontmatter 与脚本负责，不在此重复）
- "cwd 看起来像工作目录，应该直接开始写。"（× 未完成开工前预检禁止进入任何创作子技能）
- "在插件仓库根就地写一个 `summary.md` 试试。"（× 插件仓库根必须走测试模式，回写只能落在 `test/books/<book-id>/`）
- "用户没说 book-id，我先挑一个。"（× 测试模式下必须遵守 `显式 book-id > test/current-book.yaml > demo-book`；如果配置文件存在但无效，必须停下来提示，不能自己改挑别的书）
