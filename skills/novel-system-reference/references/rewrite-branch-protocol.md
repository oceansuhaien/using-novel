# 改稿分支协议

本协议用于处理“正文已经落盘，但用户后续不满意，需要返工”的场景。

默认主方案是**轻量版本分支**，目标优先级是：
1. 小说质量
2. 用户体验
3. 可追溯性
4. 实现成本

## 核心原则

- 不在当前主线上直接原地改稿。
- 先做影响面分析，再决定返工范围。
- 主线在返工期间进入**冻结仅读**状态。
- 改稿结果按受影响文件包推进。
- 整包确认后，才允许一次性合并回主线。
- 不自动全书联动改写。

## 主线与改稿分支

### 主线

主线是当前被视为“正式事实”的工作线。

在返工期间：
- 主线继续保留
- 主线不删除
- 主线默认不接收局部新稿回灌
- 主线只作为旧参考事实保留

### 改稿分支

改稿分支是针对某次返工请求建立的轻量工作线。

它不是整仓库复制，也不是完整 VCS 分支；它是单本书工作区内的返工上下文。

改稿分支至少要表达：
- 本次返工基于哪个主线状态创建
- 当前返工目标是什么
- 当前受影响文件包有哪些
- 哪些文件在当前分支里是有效输入

## 生命周期

### 1. 创建

当用户对已落盘正文提出返工请求时：
- 创建轻量版本分支
- 记录主线快照来源
- 冻结主线仅读

### 2. 分析

先生成影响面分析，不直接写新稿。

### 3. 推进

按受影响文件包逐包推进。

### 4. 确认

只有当整个返工范围内的文件包都确认通过后，才进入合并队列。

### 5. 合并

整包确认后，一次性合并回主线。

### 6. 废弃

若用户放弃本次返工分支：
- 分支可被标记为废弃
- 主线不受影响
- 旧证据保留为追溯材料

## 读取边界

在改稿分支内，默认读取：
- 当前分支自己的 `context.md`
- 当前分支里受影响的 `plot/` 文件
- 当前分支里受影响的人物资料
- 当前分支里受影响的章节材料

旧主线资料：
- 可以保留为参考
- 不再默认作为当前有效写作输入

## 合并边界

为了优先保证质量和用户体验：
- 不边改边局部回灌主线
- 不在单个子包刚通过时就改写主线
- 只有整包确认后，才一次性合并回主线

## 自动化边界

OMX 可以自动：
- 创建改稿分支
- 冻结主线仅读
- 生成影响面分析
- 组织文件包推进

OMX 不应自动：
- 全书联动改写
- 局部回灌主线
- 在用户未确认整包前把分支当成新主线
