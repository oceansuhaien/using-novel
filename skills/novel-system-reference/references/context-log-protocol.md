# `context.md` 协议

`context.md` 是单本书工作区里的**共享决策日志**。

它用于记录多轮讨论后已经拍板的关键结论、尚未解决的冲突、覆盖旧资料的依据，以及仍需用户确认的问题，方便大纲、剧情、人物三个领域技能在同一份上下文上连续工作。

## 定位

`context.md` 记录的是**决策状态**，不是完整聊天记录，也不是第二份 `summary.md`。

- `summary.md`：高层稳定状态与当前结论，方便快速回看。
- `context.md`：多轮确认过程中的关键决策、冲突、覆盖历史与待确认问题。
- 领域文件（`outline/`、`plot/`、`characters/`、`canon/`）：最终的长期资料落点。

作者级偏好、跨书复用经验与“候选经验 / 稳定规则”的升级边界，不属于 `context.md` 的主体协议；这类内容应走 `preference-memory-protocol.md`。

当进入已落盘正文的返工场景时，`context.md` 还必须区分主线与改稿分支：主线继续保留为旧事实来源，改稿分支承载当前有效改稿事实；不边改边局部回灌主线，整包确认后再一次性合并回主线。具体分支规则见 `rewrite-branch-protocol.md`。

## 与正文执行审计的边界

正文生成后的**完整审计记录**属于执行证据，不属于 `context.md` 的默认正文。

- 完整审计记录默认写到章节级证据位置，优先落在 `chapters/notes/`。
- 它用来回答“这次为什么这样写 / 为什么没补首次出场介绍 / 读了哪些上下文 / 触发了什么补救链路”。
- 它不写进 `context.md` / `summary.md` 主体。
- 只有当审计产出了会影响后续技能的稳定结论时，才允许把结论摘要式引用到 `context.md`。

### 正文执行审计至少记录什么

- 本次任务类型（扩写 / 续写 / 改写 / 润色 / 对白校正 / 过渡修复）
- 触发原因
- 读取了哪些上下文文件或证据来源
- 是否触发首次出场 / 识别锚点检查
- 为什么判定需要或不需要补介绍
- 是否触发人物一致性、剧情承接或 continuity 相关补救链路
- 是否形成了需要同步到 `context.md` 的稳定结论

### 正文执行审计默认命名

- 默认写入 `chapters/notes/scene-audit-YYYYMMDD-<scene-slug>.md`
- `YYYYMMDD` 用生成当日日期
- `<scene-slug>` 只保留当前场景或任务的最小可识别标题，例如 `ch03-card-table`、`newcomer-first-seat`
- 如果当前任务没有明确章节号，也不要发明新设定；用场景功能或用户本轮任务意图做 slug 即可

### 正文执行审计最小模板

```markdown
# 正文执行审计

- 任务类型：
- 触发原因：
- 读取的上下文：
- 首次出场 / 识别锚点检查：
- 判定理由：
- 后续动作：
- 是否同步 `context.md`：
```

说明：

- `读取的上下文` 只列本轮真正读取的文件或材料，不补猜。
- `后续动作` 只写已触发或明确建议的补救链路，例如“无”“建议转 `novel-character-card-coach`”“已补两个识别锚点”。
- `是否同步 \`context.md\`` 只回答是否形成稳定结论，不在这里重复整段故事摘要。

## 什么时候写

出现以下情况时，优先更新 `context.md`：

- 用户刚刚明确确认了一个关键结论。
- 新结论覆盖了旧结论，需要说明依据。
- 两步确认之间出现冲突，但暂时不能直接裁定。
- 某个问题必须等用户拍板，才能继续稳定回写。

## 什么时候不写

以下内容不要写进 `context.md`：

- 完整聊天逐字稿。
- 纯脑暴阶段的大量备选灵感。
- 已经稳定落盘、且没有冲突或待确认价值的细节长文。
- 章节细表、长人物卡、长篇世界观设定。
- 逐次正文生成的完整执行审计；这类执行证据默认进 `chapters/notes/`，不写进 `context.md` / `summary.md` 主体。

这些内容应分别进入 `inbox/`、`plot/`、`characters/`、`canon/` 等更窄的目录。

## 推荐区块

```text
# 项目上下文

## 会话目标
## 当前有效结论
## 最近确认
## 冲突清单
## 待用户确认
## 影响范围
## 覆盖历史
```

### 会话目标

只写当前这一轮或最近连续几轮讨论在解决什么，例如“确定主旨与第一卷方向”。

### 当前有效结论

只保留仍然生效、且会影响后续工作的关键结论。这里是领域技能进入工作前的第一阅读入口。

### 最近确认

追加记录最近一次拍板的高价值结论，便于回溯“现在为什么是这样”。

### 冲突清单

记录尚未解决、且会影响任务走向的冲突。每条冲突都应尽量写清：
- 冲突双方是什么
- 来自哪一步或哪份资料
- 为什么不能直接覆盖
- 下一步需要用户确认什么

### 待用户确认

只保留真正阻塞后续稳定回写的问题。优先记录高杠杆问题，不堆积琐碎小问答。

### 影响范围

记录本次确认会影响哪些文件，例如 `summary.md`、`outline/volumes.md`、`plot/mainline.md`、`characters/index.md`。

### 覆盖历史

当新结论明确替代旧结论时，在这里留下一条简短记录，说明：
- 新结论覆盖了什么旧结论
- 覆盖依据是什么
- 哪些文件已同步更新

## 单条记录模板

可按下面的最小格式记录：

```markdown
- 日期：YYYY-MM-DD
- 触发步骤：例如“确认第一卷方向”
- 结论：一句话写清本次拍板内容
- 证据等级：已确认事实 / 强推断 / 待确认 / 建议
- 来源：用户本轮确认 / `summary.md` / `plot/mainline.md` / 其他明确来源
- 影响文件：`summary.md`、`outline/volumes.md`
- 覆盖旧结论：否 / 是（写清被覆盖项）
- 状态：生效 / 待确认 / 已解决冲突 / 已废弃
```

不要求每次都写成长段解释，但必须让后续技能看得懂“这条结论现在是否有效”。

## 冲突处理顺序

1. 先检查用户本轮最新明确指令能否直接覆盖旧结论。
2. 若能覆盖，写入“覆盖历史”，并同步更新受影响文件。
3. 若不能直接覆盖，先把冲突写入 `context.md` 的“冲突清单”。
4. 然后只问一个最小必要问题，等用户拍板后再继续。

## 回写顺序

领域技能在处理关键确认时，推荐按这个顺序执行：

1. 更新 `context.md`
2. 更新最窄、最匹配的领域文件
3. 只把高层结果摘要同步到 `summary.md`

这样可以避免冲突过程污染 `summary.md`，也能保留覆盖依据。
